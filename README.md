# Device Management API

## 1. Description

Device Management API is a service for storing and managing
devices. It provides create, read, update, filtering, pagination, and delete
operations.

A device contains:

| Property | Description |
|---|---|
| `id` | Server-generated UUID |
| `name` | Device name, up to 200 characters |
| `brand` | Device brand, up to 100 characters |
| `state` | `available`, `in-use`, or `inactive` |
| `creationTime` | Server-generated creation timestamp in UTC |
| `version` | Optimistic-lock version |

### 1.1 Functional requirements

The service supports:

- creating a device;
- fully replacing mutable properties with `PUT`;
- partially updating selected properties;
- fetching one device by its Id;
- fetching a paginated list of devices;
- filtering devices by brand using a case-insensitive exact match;
- filtering devices by state;
- deleting a device.

Business rules:

- IDs and creation timestamps are generated by the server;
- `creationTime` cannot be changed;
- `name` and `brand` cannot be changed while the current device state is
  `in-use`;
- an `in-use` device cannot be deleted;
- invalid input returns `400 Bad Request`;
- missing devices return `404 Not Found`;
- business-rule and optimistic-lock conflicts return `409 Conflict`.

### 1.2 Non-functional requirements and assumptions

The implementation was designed for the following assumed operating ranges:

| Concern | Assumption or target |
|---|---|
| Dataset | Up to 1,000,000 devices |
| Read throughput | 200 requests per second |
| Write throughput | 100 requests per second |
| Response time | p95 below one second under the target load |
| Consistency | Read-your-writes and ACID transactions |
| Availability | Stateless API instances suitable for horizontal scaling |
| Pagination | Maximum page size of 100 |
| Time | Timestamps stored as UTC instants |

These values are test targets, not unconditional performance claims. Capacity
depends on the allocated API and PostgreSQL resources, dataset distribution,
connection-pool configuration, and deployment topology. Multi-tenancy and
authentication/authorization are outside the current scope.

## 2. Technical implementation

The service uses Spring MVC with blocking JPA/JDBC access:

```text
HTTP request
    -> generated OpenAPI interface and transport model
    -> DeviceController
    -> DeviceMapper
    -> DeviceService
    -> BusinessRulesValidator
    -> DeviceRepository
    -> PostgreSQL
```

Transport models generated from OpenAPI are kept at the HTTP boundary. The
controller maps them to application commands before calling the service.
Business rules are evaluated in the service layer, while persistence is handled
through Spring Data JPA.

PostgreSQL was selected because the model is relational and requires strong
consistency, atomic updates, optimistic locking, indexed filtering, and reliable
schema migrations. Spring MVC was selected instead of WebFlux because database
access is blocking and the expected concurrency does not justify a fully
reactive R2DBC stack.

### 2.1 API endpoints

| Method | Path | Description | Success |
|---|---|---|---:|
| `POST` | `/api/v1/devices` | Create a device | `201` |
| `GET` | `/api/v1/devices/{id}` | Fetch a device | `200` |
| `GET` | `/api/v1/devices` | List and filter devices | `200` |
| `PUT` | `/api/v1/devices/{id}` | Fully replace mutable properties | `200` |
| `PATCH` | `/api/v1/devices/{id}` | Partially update mutable properties | `200` |
| `DELETE` | `/api/v1/devices/{id}` | Delete a device | `204` |

List parameters:

| Parameter | Required | Default | Constraint |
|---|---|---:|---|
| `brand` | No | — | Case-insensitive exact match, maximum 100 characters |
| `state` | No | — | `available`, `in-use`, or `inactive` |
| `page` | No | `0` | Minimum `0` |
| `size` | No | `20` | From `1` to `100` |

Errors use the `application/problem+json` media type and the error schema
defined in the OpenAPI contract.

### 2.2 Spec-first OpenAPI

The API follows a spec-first, or design-first, workflow. The versioned source of
truth is:

```text
src/main/resources/openapi/device-management-api.yaml
```

During Maven's `generate-sources` phase, OpenAPI Generator creates:

- the `DevicesApi` Spring interface;
- request and response models;
- validation annotations;
- enum wire-value mappings.

Generated files are written to `target/generated-sources/openapi`. They must not
be edited or committed. `DeviceController` implements the generated interface,
so incompatible contract changes produce compilation errors.

Generate and compile the API types with:

```bash
./mvnw clean compile
```

When the application is running, documentation is available at:

| Resource | URL |
|---|---|
| Swagger UI | [http://localhost:8080/swagger-ui.html](http://localhost:8080/swagger-ui.html) |
| OpenAPI YAML | [http://localhost:8080/openapi/device-management-api.yaml](http://localhost:8080/openapi/device-management-api.yaml) |

Swagger UI reads the committed YAML contract directly instead of reconstructing
the API description from controller annotations.

## 3. Running and building

### 3.1 Prerequisites

- Java 21;
- Docker with Docker Compose;
- a running Docker daemon for integration and performance tests.

A system Maven installation is not required because the repository includes
Maven Wrapper.

Verify the environment:

```bash
java -version
docker version
docker compose version
```

### 3.2 Main libraries and tools

| Technology | Version | Purpose |
|---|---:|---|
| Java | 21 | Runtime and language |
| Spring Boot | 4.1.1 | Application framework |
| Spring MVC | managed by Boot | Servlet-based REST API |
| Spring Data JPA / Hibernate | managed by Boot | Persistence and optimistic locking |
| PostgreSQL | 17 | Relational database |
| Liquibase | managed by Boot | Versioned database migrations |
| OpenAPI Generator | 7.25.0 | API interfaces and transport models |
| springdoc-openapi | 3.1.0 | Swagger UI |

| JUnit 5 and Mockito | managed by Boot | Unit tests |
| Testcontainers | 2.0.5 | PostgreSQL integration tests |
| Gatling | 3.15.1 | Performance tests |

### 3.3 Building the application

Compile the project and generate OpenAPI sources:

```bash
./mvnw clean compile
```

Run all automated tests and create the executable JAR:

```bash
./mvnw clean verify
```

Docker must be running because the integration test starts PostgreSQL through
Testcontainers. To build a JAR without running tests:

```bash
./mvnw clean package -DskipTests
```

The executable JAR is created under `target/`.

To run the application against an already available PostgreSQL instance:

```bash
./mvnw spring-boot:run
```

### 3.4 Docker

Build and start the API together with PostgreSQL:

```bash
docker compose up --build -d
```

Check the environment:

```bash
docker compose ps
docker compose logs -f api
```

The API is available at:

```text
http://localhost:8080/api/v1/devices
```

Stop the environment while preserving PostgreSQL data:

```bash
docker compose down
```

Remove the environment and its PostgreSQL volume:

```bash
docker compose down -v
```

The last command permanently deletes the local database data.

## 4. Tests

### 4.1 Unit tests

Unit tests cover service behavior, business validation, mapping, query-parameter
conversion, and PATCH missing-versus-null semantics.

Run only unit tests:

```bash
./mvnw -Dtest='*Test,!DeviceApiIntegrationTest' test
```

### 4.2 Integration tests

`DeviceApiIntegrationTest` starts the full Spring context and a real PostgreSQL
container. Liquibase applies migrations, and MockMvc exercises the complete
controller-to-database path without opening a server port.

Covered behavior includes create, fetch, list, filtering, `PUT`, `PATCH`, delete,
pagination constraints, and `in-use` business rules.

Run the integration test:

```bash
./mvnw -Dtest=DeviceApiIntegrationTest test
```

Docker must be running. Testcontainers manages the PostgreSQL lifecycle and
provides the datasource connection to Spring Boot.

Run all unit and integration tests:

```bash
./mvnw test
```

### 4.3 Performance tests

Gatling runs against an isolated Docker Compose environment on port `18080`.
The target load is 200 read and 100 write requests per second. The full profile
prepares a dedicated database containing up to one million devices.

Run a short smoke profile:

```bash
PERF_PROFILE=smoke ./performance/run-gatling.sh
```

Run the target load profile:

```bash
./performance/run-gatling.sh
```

The runner starts the performance stack, waits for readiness, loads performance
data, executes Gatling, and stops the containers. Its PostgreSQL volume is
preserved between runs. HTML reports are written under:

```text
target/gatling/
```

Detailed options are documented in [performance/README.md](performance/README.md).

|---|---|---|

| `DB_USER` | `devices` | PostgreSQL user |

| `JAVA_TOOL_OPTIONS` | — | Optional JVM runtime settings |

Production credentials must be supplied through an appropriate secrets

### 5.2 Production profile

Activate the hardened production configuration with:

```bash
SPRING_PROFILES_ACTIVE=prod java -jar target/device-management-api-*.jar
```

The production profile requires `DB_URL`, `DB_USER`, `DB_PASSWORD`, and
`DB_SSL_ROOT_CERT`. PostgreSQL TLS defaults to `verify-full`, which encrypts the
connection and verifies the server certificate and hostname. Do not weaken it
to `require` unless certificate verification is deliberately handled elsewhere.

| Variable | Default | Description |
|---|---:|---|
| `DB_SSL_MODE` | `verify-full` | PostgreSQL TLS verification mode |
| `DB_SSL_ROOT_CERT` | required | Mounted CA certificate path |
| `DB_POOL_MIN_IDLE` | `5` | Minimum idle database connections |
| `DB_CONNECTION_TIMEOUT_MS` | `3000` | Connection acquisition timeout |
| `DB_VALIDATION_TIMEOUT_MS` | `1000` | Connection validation timeout |
| `MANAGEMENT_SERVER_PORT` | `8081` | Separate Actuator port |
| `SHUTDOWN_TIMEOUT` | `30s` | Graceful shutdown timeout |

Swagger, the static OpenAPI document, detailed health output, and the metrics
endpoint are disabled in this profile. The management port must additionally be
restricted by a private network, firewall, Kubernetes NetworkPolicy, or reverse
proxy. Secrets should be mounted or injected by the deployment platform and
must not be committed to Compose files or the repository.

### 5.3 Health and observability

| Endpoint | Purpose |
|---|---|
| `/actuator/health` | Overall application health |
| `/actuator/health/liveness` | Process liveness |
| `/actuator/health/readiness` | Readiness including PostgreSQL availability |
| `/actuator/health/db` | Direct datasource health |
| `/actuator/metrics` | Application metrics |

Database failure makes readiness `DOWN`, while liveness remains independent to
avoid restart loops during a database outage. Detailed health information is
enabled for this exercise; production deployments should restrict access to
management endpoints and sensitive health details.

Useful commands:

```bash
docker compose logs -f api
docker compose logs -f postgres
docker compose exec postgres pg_isready -U devices -d devices
```

## 6. Design decisions and limitations

- Database schema changes must be introduced as new Liquibase changesets.
  Applied changesets must not be modified.
- `PUT` replaces all mutable properties, while `PATCH` uses JSON Merge Patch to
  distinguish missing fields from explicitly supplied `null` values.
- Offset pagination is sufficient for the current API contract and page-size
  limit. Keyset pagination should be considered for deep sequential traversal.
- Device listings use slice pagination. The response exposes `hasNext` instead
  of `totalElements` and `totalPages`, avoiding a database count query for every request.
  For high read loads, a `Slice`/cursor response or cached counters may be more
  appropriate.
- The API is stateless, but PostgreSQL remains the consistency and write-scaling
  boundary.
- Authentication, authorization, TLS termination, backup/restore, centralized
  logging, dashboards, and alerting are deployment concerns outside the current
  challenge scope.
- Performance targets must be verified in a production-like environment with
  recorded CPU, memory, JVM, connection-pool, and PostgreSQL metrics.
